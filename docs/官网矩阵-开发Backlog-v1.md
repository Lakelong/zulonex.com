# 逐鹿未来项目官网矩阵：MVP 开发 Backlog

> 版本：v1.0  
> 日期：2026-07-30  
> 目标：将需求基线拆分为可以估时、排期和验收的工程工作

## 1. 计划假设

- 新项目使用独立仓库；
- 团队采用 TypeScript；
- 一套 Web 应用承载公众站、运营后台和受控 API；
- 一个异步 Worker 承载 AI、发布和同步；
- PostgreSQL、Redis、对象存储为核心依赖；
- 首批 10–20 个真实城市；
- 首期所有正式内容人工批准；
- CRM 目标在 M0 确认；
- 不在 MVP 提供面向公众的开放式 AI 聊天。

## 2. 团队建议

- 1 名技术负责人/架构；
- 2 名全栈工程师；
- 1 名后端/AI 工程师；
- 1 名产品设计；
- 1 名 QA/测试；
- 内容、SEO、业务和合规负责人兼职参与。

若只有 2–3 名工程人员，应保持同一架构但减少并行，不能删除审批、隐私、回滚和 Eval。

## 12. 关键路径

```text
M0 决策
 -> 独立仓库/环境/DB
 -> Region + Claims + Content Schema
 -> 公众页面 + 审核发布
 -> 线索路由
 -> AI 工具和 Agent
 -> Eval
 -> 真实城市数据
 -> 试点上线
```

不能为了提前演示 AI 而跳过 Claims、内容 Schema、权限和审批。否则 Agent 只能生成无法安全发布的文本。

## 13. Sprint 建议

以双周 Sprint 为例：

| Sprint | 重点 |
| --- | --- |
| S0 | M0 决策、建仓和 UX 方向 |
| S1 | 工程底座、DB、RBAC、城市模型 |
| S2 | 设计系统、核心主站、门店模型 |
| S3 | 城市页、Claim/Evidence、内容 Schema |
| S4 | 编辑、审核、发布、SEO |
| S5 | 线索、路由、CRM、分析 |
| S6 | Agent 工具、Brief、草稿 |
| S7 | 核验、合规、Eval、Pilot 准备 |
| S8 | 试点灰度、修复和上线 |

在 5–6 名跨职能成员可并行的前提下，技术 MVP 约 8–12 周；真实搜索和转化验证另需 4–8 周观察。具体时间必须在 M0 决策和任务二次拆分后重估。

## 14. Definition of Done

每个任务完成必须满足适用项：

- 代码评审；
- 单元/集成测试；
- 类型和 Schema 校验；
- 权限和审计测试；
- 失败、重试和幂等测试；
- 不记录敏感信息；
- 可观测性；
- 文档或 Runbook；
- preview 验证；
- 产品/业务验收；
- 高风险功能完成合规验收；
- 不留下绕过审批的临时入口。

## 15. 上线阻断条件

出现以下任一项不得上线：

- 域名、主体或品牌授权未确认；
- 公开门店或业务数字无法核验；
- 高风险内容存在 blocker；
- PII 明文进入日志、分析或 Agent trace；
- 城市页仅替换地名；
- Sitemap 包含 `noindex` 或未批准页面；
- 线索可能丢失或错误跨城市分配；
- CRM 故障导致前台无法保存；
- Agent 具有直接发布、原始线索或任意数据库权限；
- 备份、回滚和 Kill Switch 未验证；
- Eval 中已知高风险案例仍可通过。
