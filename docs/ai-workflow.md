# AI Native 协作与线程管理规范

本文档用于规范 ZULONEX 官网项目中人和 AI 的协作方式。目标是让需求、上下文、实现、验证和交接都沉淀在项目里，而不是散落在多个对话窗口中。

## 基本原则

- GitHub 仓库和项目文件是唯一事实源，对话记录只作为临时工作空间。
- 一个线程对应一个清晰目标，不要让多个线程同时修改同一批文件。
- 重要结论必须回写到 `docs/`、`src/content/` 或代码注释中，不能只停留在聊天里。
- 每次实现都要有验证动作，至少运行 `npm run check` 和 `npm run build`。
- 结束一个线程前，必须说明改了什么、验证了什么、还有什么未处理。

## 线程是什么意思

这里的“线程”可以理解为一个对话窗口，也可以理解为一个工作泳道。推荐把一个对话窗口当成一个线程来管理。

一个线程应该只服务一个主要目标，例如：

- 官网首页视觉刷新
- 合作校项目单页
- 案例与洞察内容维护
- 部署与线上问题排查
- 品牌资料整理

不要在同一个线程里同时做设计、部署、内容录入、Bug 修复和新功能开发。可以顺手处理强相关的小问题，但不要把线程变成杂货筐。

## 推荐窗口分工

日常维护官网时，建议保留 3 类窗口：

1. 主开发线程
   - 当前真正改代码的窗口。
   - 一次只处理一个页面、一个模块或一个明确问题。
   - 所有文件修改、构建验证、浏览器检查都在这里完成。

2. 资料整理线程
   - 用来整理 PDF、Word、PPT、会议记录、品牌资料和业务口径。
   - 输出应沉淀到 `docs/briefs/`、`docs/decisions/` 或 `src/content/`。
   - 不直接改页面代码，避免和主开发线程冲突。

3. 发布运维线程
   - 用来处理 GitHub、部署、域名、环境变量、线上回滚和故障排查。
   - 只在需要发布或查线上问题时启用。
   - 不夹带新的设计改版需求。

如果项目阶段比较小，也可以只保留一个主开发线程。但当你开始多设备、多窗口协作时，应按上面的职责拆开。

## 什么时候新开线程

建议新开线程的情况：

- 目标变了，例如从“项目单页排版”变成“部署上线”。
- 需要长时间调研资料，不想污染当前代码实现上下文。
- 当前线程已经很长，里面混入了大量过期讨论。
- 要让 AI 接手一个相对独立的新页面、新模块或新文档。
- 需要另一个窗口只做 review、验收或问题标注。

不建议新开线程的情况：

- 只是当前页面上的几个小样式问题。
- 只是继续修复刚刚构建报错。
- 只是补充同一份文档的内容。
- 只是让 AI 解释刚刚改过的代码。

## 线程命名规则

对话窗口标题建议使用：

```txt
ZULONEX 官网｜目标｜状态
```

示例：

```txt
ZULONEX 官网｜合作校单页｜设计实现
ZULONEX 官网｜案例与洞察｜内容维护
ZULONEX 官网｜发布上线｜生产验证
ZULONEX 官网｜品牌资料｜口径整理
```

状态可以使用：

- `规划`
- `设计实现`
- `内容维护`
- `问题修复`
- `生产验证`
- `已完成`

## 每个线程的启动模板

开启新线程时，建议直接给 AI 这段信息：

```md
这是 ZULONEX 官网项目。

本线程目标：

相关页面或文件：

资料来源：

设计或内容要求：

验收标准：
- npm run check 通过
- npm run build 通过
- 浏览器检查关键页面

请先阅读相关代码和文档，再实施，不要大改无关模块。
```

如果已有旧线程，可以补一句：

```md
请不要依赖旧对话记忆，以项目文件为准。必要上下文我会补充。
```

## 每个线程的结束模板

一个线程结束前，应让 AI 输出：

```md
本次完成：

修改文件：

验证结果：

后续维护方式：

遗留问题：
```

如果后续要交给另一个线程继续，应把这段结束说明复制给新线程，或者整理进 `docs/briefs/`。

## GitHub 与分支管理

- `main` 保持可发布状态。
- 大改动使用功能分支，例如 `feature/project-page-xinglu`。
- 修复线上问题使用修复分支，例如 `fix/cooperation-link`。
- 一个分支尽量对应一个目标，避免把多个业务需求揉在一起。
- 提交前先看 `git status --short --branch`，确认没有混入无关文件。
- 提交信息写清楚业务目的，而不是只写 `update`。

推荐流程：

```txt
需求 brief -> 新建分支 -> AI 实现 -> 本地验证 -> 人工浏览器标注 -> AI 修正 -> 构建通过 -> commit -> push -> PR 或部署
```

## 项目内沉淀位置

- 业务资料和决策：`docs/`
- 临时需求说明：`docs/briefs/`
- 重要方案取舍：`docs/decisions/`
- 案例与洞察：`src/content/insights/`
- 项目单页内容：优先沉淀为数据或独立页面目录
- 图片素材：`src/assets/` 或 `public/assets/`

新增页面、内容体系或维护规则时，必须同步补文档。这样下一个线程才能从文件中接上，而不是靠回忆上一段对话。

## 多设备使用建议

- 同一时间只让一个设备上的一个线程拥有“写代码权限”。
- 其他设备可以看资料、做标注、整理文案，但不要同时要求 AI 改同一批文件。
- 如果必须切设备，先让当前线程输出结束模板，再把结果带到新设备。
- 浏览器标注非常适合做验收，但标注内容也应最终转化为代码修改或文档说明。

## 判断线程是否健康

健康线程通常具备：

- 目标一句话能说清。
- AI 知道当前应该改哪些文件。
- 验收标准明确。
- 代码、文档和浏览器结果能相互印证。

需要收束或重开线程的信号：

- 同一窗口里出现多个互相无关的目标。
- AI 开始反复问已经回答过的问题。
- 旧方案和新方案混在一起，页面越改越偏。
- 你自己也说不清这个窗口现在到底负责什么。

遇到这种情况，不必硬撑。让 AI 输出当前状态摘要，沉淀到 `docs/briefs/`，再开一个干净线程继续。
